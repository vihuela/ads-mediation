## Why

当前 SDK 仅支持开屏、插屏和激励广告，缺少页面底部 Banner 的正式 View 与 Compose 接入能力。Banner 的持续展示、平台刷新及单 Activity 页面导航需要独立的页面资格、资源释放和事件归因契约，避免重组或 Tab 切换重复请求、离页后旧广告回挂，以及刷新后的曝光和收益漏记。

**2026-09-29 已批准的首版范围修订：先交付 AdMob 直连正式 View／Compose Banner，TopOn 正式展示与收益接入暂缓。** 当前 TopOn 探针及其反例证据继续保留在 [verification.md](verification.md)；公开请求仍可明确选择 TopOn，但须在进入 TopOn Banner SDK 加载前返回可诊断的 unsupported 失败，不自动回退 AdMob。后续补齐 TopOn 须单独通过尺寸、刷新配置、展示身份和收益归因门槛；探针可编译或局部可见不等于正式支持。

## What Changes

- 新增 AdMob 直连 Banner 正式接入，提供 SDK 自有的 `AdsBannerView` 和请求参数。`BannerRequest` 显式指定平台、Banner 广告位 ID、业务 position 和 `Standard320x50`／`AnchoredAdaptive` 尺寸；AdMob 复用初始化与请求前 UMP 门禁，检查自身初始化结果，包括 Bidding 部分初始化失败的情况。TopOn 选择明确失败，不自动切换平台或回退到全屏广告 ID。
- 正式提供可选 Compose 薄模块及 `AdsBanner()`，复用 View 的资格、布局和释放逻辑。普通重组、等值请求、回调更新和页面内部 Tab 切换不额外加载；页面 owner、Activity 或请求实际改变时建立新实例，Preview 仅显示占位。
- 区分页面业务资格 `active` 与临时显示资格 `visible`，结合页面 owner、Activity、窗口、宿主可见性及有效宽度控制请求和挂载。导航离开结束广告位周期，临时覆盖或退后台按已验证的平台策略暂停与恢复；owner 销毁及最终释放均幂等，同广告位 ID 的多个 View 保持实例和身份隔离。
- 平台实例自创建或回调交付时起即承担释放责任，覆盖配置异常和加载中离开；旧加载与 UI 回调不能恢复已结束实例或影响新页面。收益监听在平台允许的最早时点注册，并先于可能触发展示的业务回调及首次可见，允许经资格复核的不可见空 View 预挂载；各业务回调的异常不得阻断其他合法出口或资源清理。
- 容器按宿主实际内容宽度、合法广告尺寸及测量结果自适应高度，View 与 Compose 均不固定为 50 dp。仅有效请求尺寸变化才允许重建平台实例，广告高度变化不额外加载；固定尺寸放不下时明确失败，加载前占位与首次失败恢复须共同验证。
- 自动刷新交由 AdMob 管理，不叠加本层定时器或失败递归重试。持续展示以开启平台刷新为接入基线；关闭刷新时本层不补充重试，刷新失败保留仍有效的旧广告。首次无填充或断网后的同页恢复须独立验证，不能用已展示广告的刷新结果替代；TopOn 下层防重复刷新配置留待后续接入核验。
- 保留广告位进入、加载、刷新、曝光、点击、收益及有明确平台语义的展示失败和关闭事件，新增 `ad_banner_refresh` 与可选 `slotId`，沿用统一事件和收益出口。区分 slot、真实本层 request 和单次展示 session，支持刷新后的独立曝光、各事件去重、曝光与收益先后互换及合法零收益；已确认身份的迟到收益仍归原展示，未知归因不得冒充当前广告或伪造收入。
- **BREAKING（宿主源码适配风险）**：扩展 `AdFormat.BANNER` 和事件枚举后，宿主穷尽 `when` 分支需适配，事件解析与报表需识别 Banner 的持续展示语义。全屏专用入口明确拒绝 BANNER，已有全屏等待机会、缓存竞价、互斥及一次性事件终态保持原契约。
- 首版不包含跨 SDK Banner 比价、跨页面 View 搬运或缓存池、任意外部容器绑定框架、Inline／可折叠／原生混排、SDK 自建关闭按钮、显式重试 API，以及运行期间隐私变化监听；不借此扩展通用广告框架或升级广告 SDK。

## Capabilities

### New Capabilities

- `banner-display`: 定义首版 AdMob 页面底部 Banner 的 View 与 Compose 接入、TopOn 选择时的明确不支持结果、请求资格、页面归属、暂停恢复与释放、自适应布局、平台刷新，以及事件和收益身份契约；保留 TopOn 后续接入门槛。

### Modified Capabilities

无。项目当前没有已登记的能力规范；进行中的 `fullscreen-display-opportunities` 变更保持原范围，本变更仅增加 Banner 与全屏入口的隔离要求。

## Impact

- 核心与公共 API：涉及 Banner 请求、View、格式及事件字段扩展、AdMob 正式接入与 TopOn 不支持边界、初始化状态读取、日志和收益分发；需检查现有按广告格式分支的配置、加载及展示入口，并记录实际源码与二进制兼容影响。
- 构建与交付：核心 AAR 保持 View 能力，新增可选 Compose 扩展模块，核心不引入 Compose 或 Navigation 依赖。模块名、发布坐标和最低依赖版本在验证现有工程后确定；广告依赖沿用声明的 GMA Next-Gen 1.2.1、TopOn 6.6.22.3、GMA adapter 1.2.1.1.0 和 UMP 4.0.0，以实际解析结果复核。
- 平台能力门槛：AdMob 正式路径仍须验证锁定版本的真实 API、尺寸与占位、暂停路径、首次失败恢复、连续刷新及曝光／收益身份。TopOn 探针的尺寸偏差、showId 复用和刷新配置未知见 [verification.md](verification.md)，这些未通过项阻止正式接入；未来须先解决并独立验证，不将官方较新版本说明或旧工程行为当作当前能力证据。
- 产品选择：页面独立持有作为默认示例，公共底部布局作为可选接入；跨页面共用实例、首次无填充后收起槽位、所有临时暂停统一释放重建仍未确认。规划沿用现有方案的占位和按平台能力暂停建议，不将这些体验取舍写成已接受要求。
- 验证与文档：以[现有 Banner 方案](../../../../docs/banner-implementation-plan.md)为依据，后续 specs、design 和 tasks 承接其契约及验收矩阵。补充 View／Compose 宿主接入、平台刷新配置和事件映射说明，分别记录受控回调测试、编译、Release／R8、设备行为及视觉验收结果；本 proposal 不代表 Banner 已实现或已通过验证。
